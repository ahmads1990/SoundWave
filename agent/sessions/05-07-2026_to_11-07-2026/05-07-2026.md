### [00:36:00] - Architecture Discussion: Read Context / Read Repository
- Discussed the added value of introducing a dedicated read context and read-only repository.
- Key benefits: read replicas (biggest win), no tracking overhead by default, swappable read stack (Dapper, ES, OLAP), separate migration strategy.
- Decision: defer to later (before Phase 4 Analytics or Phase 5 Search).

### [00:56:00] - Architecture Discussion: Commands That Read Before Mutating
- Clarified that commands needing read-then-mutate (e.g., `ApproveArtistCommand`) must use the **write repo**, not the read context.
- Reason: stale data risk from replicas, and change tracking is needed for EF `SaveChanges()`.
- Rule established: if the handler calls `SaveChanges()`, it uses the write repo. Period.

### [00:58:00] - Architecture Discussion: Multiple Read Contexts
- Clarified that you don't need a separate `DbContext` per read backend.
- OLAP/replica → single read `DbContext` with different connection string.
- ElasticSearch → `ISearchService` (no DbContext). Qdrant → `IRecommendationService` (no DbContext).
